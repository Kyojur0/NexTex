# MCP integration

The requested integration exposes NexTex to standard MCP clients over local
Streamable HTTP (`/mcp`) and stdio. Both transports use the same tool definitions
and existing filesystem/compiler API. A browser WebSocket bridge makes the open
editor's unsaved source and normal save, build and undo operations available.

## Implementation

- Add protocol tests for tool discovery, workspace CRUD, revision conflicts,
  compilation/PDF retrieval, transport errors and localhost restrictions.
- Add a bounded browser-session broker with ordered commands, disconnect handling
  and timeouts; test independently with disposable sessions.
- Connect the frontend store through typed commands. Require document identity
  and source hashes before agent edits, preserving undo and recovery behavior.
- Mount the official Python MCP SDK in the API lifespan; add a stdio adapter.
- Document client configuration and example workflows in a short MCP guide.
- Run existing checks/build and verify both transports plus a real browser session
  against an isolated workspace before enabling the local running application.

## Boundaries

Tools operate in the currently selected workspace. Workspace changes remain in
the app so an agent cannot grant itself access to a new directory. Saved-file
writes require the revision returned by a read; live edits require a fresh source
hash. Tool arguments and document text are data, with no arbitrary code execution
tool. HTTP and browser connections retain localhost Host/Origin checks. Multiple
browser tabs have explicit session identifiers; no tab is selected implicitly.

Browser commands: `read`, `open`, `set_content`, `save`, `save_as`, `build`, `undo`,
`redo`, `set_mode`. State includes workspace, path, source, revision, dirty/busy
flags, mode, undo availability and PDF URL. Commands return the resulting state;
timeouts instruct clients to reread before retrying because a command may finish.

## Verification

Implemented with 15 shared tools and the workspace resource. The production app
serves HTTP MCP and the stdio launcher connects to the same running backend.
Client configuration is in `docs/mcp.md`.

- Full check passed: 132 frontend tests, TypeScript, lint (two existing warnings)
  and 131 backend tests. The subsequently added MCP compiler-shutdown regression
  also passes; all 41 affected backend tests passed together.
- Production build passed. Real SDK clients verified HTTP and stdio discovery,
  file operations, compilation and PDF retrieval in disposable workspaces.
- Live browser MCP acceptance passed, including unsaved source, stale rejection,
  undo/redo, save, mode changes and a real PDF build.
- Full browser run passed 19/20. The existing keyboard-reorder test issued its
  next key before drag initialization completed. It now waits for the observable
  drag state and destination; three consecutive runs passed. All 20 scenarios
  are verified across these runs.
- The local production server was restarted and both transports independently
  discovered all 15 tools. Existing browser tabs need one refresh to load the
  new frontend bridge. User resume files were excluded from these changes.
